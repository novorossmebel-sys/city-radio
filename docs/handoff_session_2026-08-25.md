# City Radio — Хендоф (сессии 20–25.08.2026)

**Репозиторий:** github.com/novorossmebel-sys/city-radio (ветка `main`)
**Продолжение:** `docs/handoff_session_2026-08-19.md` (там был построен дайджест-движок — сбор/скоринг/маршрутизация 19 рубрик, три плановых выпуска). Эта сессия — про то, что вскрылось после суток-двух реальной работы движка без присмотра: зависания, тихие падения, утечка диска, потеря Telegram-аккаунта наблюдателя, и в итоге — полный переезд бота с ноутбука на сервер.

**Статус коммитов:** в отличие от предыдущих сессий, всё закоммичено и запушено в `main` (10 коммитов, `9f937c0` … `ea1ea68`). Ничего не висит несохранённым.

## 1. Задача и цель

Явной единой задачи на старте не было — сессия шла в режиме «проверяй, как дела» (владелец периодически спрашивал о состоянии бота), и по ходу проверок вскрывались реальные проблемы, которые чинились по мере обнаружения. Отдельно владелец сам поднял две задачи: подключить публикатор **MAX** и достать ключ **TMDB** для постеров фильмов. В середине сессии Telegram-аккаунт наблюдателя получил бан с отклонённой апелляцией — это заставило сменить номер и, в конце концов, перенести весь бот на VPS, чтобы устранить причину бана.

## 2. Что сделано — по темам

### 2.1 Watchdog для зависаний Telethon (`supervisor.py`)

**Проблема:** `run.py serve` завис на несколько часов ночью 20.08 — Telethon-клиент попал в реконнект-шторм (`MsgidDecreaseRetryError` + `readexactly() called while another coroutine is already waiting`), которая забила общий asyncio event loop и выглядела как «база данных заблокирована», хотя WAL-фикс из прошлой сессии тут был ни при чём — это другой класс проблемы (не гонка писателей, а зависший цикл событий).

**Решение:** `content/digest_engine.py::collect_candidates()` теперь безусловно пишет метку времени в `scheduler_heartbeat.txt` в конце каждого прогона. Новый `supervisor.py` (команда `run.py serve-supervised`) запускает `run.py serve` как дочерний процесс и раз в 5 минут проверяет возраст этой метки; если она не обновлялась >30 минут (или процесс сам умер) — убивает и перезапускает дочерний процесс и шлёт владельцу уведомление в Telegram («⚠️ Планировщик перезапущен автоматически: ...»). С этого момента бот всегда запускается через `serve-supervised`, а не голый `serve`.

### 2.2 Тихие падения плановых выпусков

**Проблема:** первый же боевой запуск `compose_weekly` (пятница 12:00) и один запуск `compose_evening_digest` упали с `ConnectTimeoutError` (временный сбой соединения с api.telegram.org). APScheduler такие ошибки просто логирует внутри себя — владельцу ничего не пришло, а поскольку Weekly — это раз-в-неделю cron без повтора, тот выпуск бы тихо пропал до следующей пятницы.

**Решение:** все 4 cron-задачи сборки выпусков в `scheduler.py` обёрнуты в `_safe()` — ловит исключение, логирует и шлёт владельцу уведомление. Пропущенный Weekly в тот же день довыпущен вручную (12 материалов).

### 2.3 Видео, скачанное под видом фото + утечка `media_cache/`

**Проблема:** `_download_photos` в `content/news.py` иногда сохраняла видео из смешанного альбома под расширением `.jpg` (вероятная причина: `client.download_media(msg, ...)` брало не тот компонент сообщения). Один такой файл (31.5 МБ) реально сломал отправку Weekly Digest — Telegram отклоняет фото тяжелее 10 МБ — и оставил зависший фантомный черновик в очереди модерации. Отдельно — `media_cache/` разросся до **2.6 ГБ**, потому что картинки кандидатов, отсеянных в ARCHIVE/DROP (не дошедших до модерации), никогда не удалялись.

**Решение:** скачивание теперь берёт `msg.photo` явно (не весь `msg`), добавлены проверки на video/gif/video_note, жёсткий потолок 9 МБ на скачанный файл. Добавлен `_cleanup_item_images()`, вызываемый в `digest_engine.py` на каждой ветке DROP/ARCHIVE. Разовая ручная чистка освободила 2.68 ГБ.

### 2.4 Фантомные черновики при сбое отправки фото

**Проблема:** если отправка фото с черновиком падала, `send_draft()` всё равно помечал черновик как «отправлен» — в очереди модерации навсегда оставалась невидимая запись, которую нельзя ни одобрить, ни отклонить.

**Решение:** новый `_send_text_with_keyboard()`; при сбое отправки фото — одна попытка повтора через 3 секунды, затем откат на отправку только текстом вместо тихой потери.

### 2.5 Статус кандидата не обновлялся после решения модератора

**Проблема:** после approve/reject карточки в Telegram сам пост публиковался/отклонялся нормально, но соответствующая запись в `digest.db` навсегда оставалась в статусе `sent_moderation` — не влияло на публикацию, но ломало внутреннюю статистику и отладку.

**Решение:** `Draft` (в `content/base.py`) получил поле `candidate_ids: list` (список, а не одно значение — синтез мнений о кино в `digest_compose.py` может объединять несколько кандидатов в один черновик). Заполняется и в NOW-пути (`_build_draft_for_now`), и в пакетных выпусках (`_draft_from_dict`/`_dispatch_digest`). Обработчики approve/reject в `moderation.py` теперь вызывают `update_candidate_status(cid, "published"/"dropped")` для каждого id. Проверено на живых данных 24.08 — в базе появилась первая запись со статусом `published`.

### 2.6 Рандомизация времени опроса (антибот-мера)

Добавлен джиттер к двум interval-задачам сбора кандидатов в `scheduler.py` (`jitter=180` для быстрого опроса алертных каналов, `jitter=600` для обычного), плюс случайная пауза 1.5–4.5 сек между каналами внутри одного прогона `collect_candidates`. Cron-задачи сборки выпусков (Morning/Evening/Weekly/юмор) намеренно **не** трогали джиттером — они читателю-ориентированы, время публикации должно быть предсказуемым.

### 2.7 Потеря Telegram-аккаунта наблюдателя и переезд на VPS

**Проблема:** сессия наблюдателя дважды падала с `AuthKeyDuplicatedError` («используется с двух разных IP одновременно») — 22.08 и 24.08. Первое падение совпало с блокировкой аккаунта Telegram за нарушение правил; апелляция через @SpamBot была **отклонена окончательно** — тот номер для этой роли мёртв. Второе падение (уже на новом номере) вскрыло настоящую причину: одновременно с работой бота на ноутбуке владелец включил личный VPN (Clash Verge, TUN-режим) для повседневных задач — при переключении VPN меняется исходящий IP ноутбука прямо посреди активной MTProto-сессии, что и вызывает эту защитную блокировку со стороны Telegram.

**Решение:** зарегистрирован новый номер `+6288221692812`, выполнен вход через Telethon (`telethon_login.py request`/`confirm`). Чтобы устранить причину навсегда (а не просто отложить), весь бот **перенесён на VPS** — стабильный выделенный IP, не зависящий от VPN-активности личного устройства. Это осознанно не решает более общий риск («выглядит как бот» — общий `api_id`, скриптовый паттерн опроса; вот тут и помогает джиттер из §2.6), но полностью убирает конкретный триггер IP-скачков.

### 2.8 Публикатор MAX доведён до рабочего состояния

`publishers/max.py` был написан заранее, но никогда не проверялся на живом токене. Владелец создал бота через @MasterBot (теперь проходит модерацию на стороне MAX, до суток — раньше токен выдавался мгновенно), передал токен. Единственная реальная ловушка: то, что видно в ссылке канала (`id231536618490_biz`), — это публичный слаг, не `chat_id`; при прямой отправке по слагу — `400 proto.payload`, по числовой части без префикса/суффикса — `404 chat.not.found`. Настоящий числовой `chat_id` (`-77492823908995`, с минусом, как у Telegram) найден через `GET {MAX_API_BASE}/chats` под токеном бота — этот метод перечисляет все чаты бота с их реальными id, пригодится при добавлении второго города. Подтверждено реальной публикацией.

### 2.9 TMDB-постеры для кино-рубрик

Владелец зарегистрировал бесплатный TMDB-ключ (Developer Plan) — по пути чуть не попал на платный Commercial Plan ($149/мес), потому что честно ответил «да, коммерческое использование» (это действительно бизнес-проект); подсказал вернуться на предыдущий шаг и ответить «нет» на вопрос про выручку/MAU, что верно маршрутизирует на бесплатный план. Новый `content/tmdb.py::fetch_poster(title)` ищет через `/search/multi` и скачивает постер первого результата в `media_cache/`; подключено в `digest_engine.py::_process_item` для типов `CINEMA_RELEASE/TRAILER/CASTING/REVIEW/ANALYSIS` — заменяет собой картинку из исходного поста (владелец хотел именно постер, а не старый YandexART-фоллбэк).

*Побочная, не влияющая на бота деталь:* themoviedb.org недоступен именно через связку Clash Verge/TUN на ноутбуке владельца (с VPS работает нормально, с телефона на мобильном интернете без VPN — тоже нормально) — не докопались до первопричины (подозрение на слой fake-ip DNS в TUN-режиме), но это не мешает боту, так как он работает на VPS. Оставлено как есть по договорённости с владельцем.

## 3. Что проверено живьём (по состоянию на 24.08, конец сессии)

## 5. Инструменты и сервисы, использованные в сессии

- **YandexGPT / YandexART** — без изменений, продолжают использоваться движком для рерайта и как фоллбэк-иллюстратор.
- **TMDB API** (`api.themoviedb.org`, `image.tmdb.org`) — новое: реальные постеры фильмов вместо AI-иллюстраций для кино-рубрик.
- **MAX Bot API** (`platform-api.max.ru`) — новое: второй публикатор наравне с Telegram, подтверждён на живом токене.
- **Telethon (MTProto)** — новый номер-наблюдатель `+6288221692812` после блокировки старого.
- **systemd** (VPS) — новое: `city-radio-scheduler.service`/`city-radio-moderate.service`, `enable --now`, переживают перезагрузку сервера; заменяет ручной PID-менеджмент на Windows.
- **VPS 85.31.237.212** (Hostinger KVM 1, Ubuntu 24.04, `/opt/city-radio`) — новое постоянное место работы бота; тот же сервер уже держит личные VPN-прокси владельца (mtg/Shadowsocks), запас мощности большой.
- **Paramiko (SSH/SFTP из Windows)** — перенос файлов состояния (`.env`, сессия Telethon, `digest.db`, `moderation_state.json`, `media_cache/`) на VPS, управление systemd-сервисами удалённо.
- **Clash Verge Rev** (личный VPN владельца, не часть бота) — упомянут только как источник бага §2.7; настройка и правила исключений (Яндекс/VK/Avito/MAX/Ozon — прямое соединение, остальное — через VPS) сделаны отдельно от кода проекта.

## 6. Что не сделано / открытые задачи

Отложено по явному решению владельца — не поднимать без его инициативы:
1. **Форма обратной связи от жителей** — не раньше конца сентября 2026.
2. **Переход с приватной группы на настоящий канал в Telegram** — только когда всё будет «100% отлажено», ждать сигнала от владельца.
3. **Фотозаголовки для рубрик** без своей иллюстрации — идея снята полностью («передумал»), не поднимать.

Технически открыто, но не блокирует работу:
4. **Загрузка изображений в MAX** — публикатор пока шлёт только текст (`publishers/max.py` тихо пропускает `image_paths`), картинка есть только в Telegram-версии поста.
5. **Семантический дедуп по эмбеддингам** (пороги 0.86/0.94 из редполитики) — по-прежнему заменён на LLM-дедуп по `event_key`, откалибровать позже.
6. **Таблица `movies`/`movie_id`** — группировка кино-кандидатов в `digest_compose.py` всё ещё по текстовому совпадению названия, не по ID.
7. **themoviedb.org недоступен через Clash на ноутбуке владельца** — не влияет на бота (работает на VPS), не докопались до первопричины, оставлено как есть.
8. **Личный VPN-роутер** — обсуждалась покупка (Netcraze Start NC-1112), отложена владельцем («куплю другой»).

## 8. Как продолжить в новой сессии

Прочитать этот файл + `docs/handoff_session_2026-08-19.md` (архитектура дайджест-движка) + `docs/plan_city_radio.md`. Порядок деплоя изменился: разработка и `git push` — на Windows, применение — по SSH на VPS (`git pull`, при необходимости `pip install -r requirements.txt`, `systemctl restart city-radio-scheduler city-radio-moderate`). Перед тем как диагностировать «бот молчит» по одной лишь БД — сверяться с владельцем (см. `[[feedback_verify_before_diagnosing_digest_bugs]]` в памяти, уже был один ложный вывод на этом).
