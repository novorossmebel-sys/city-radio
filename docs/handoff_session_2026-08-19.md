# City Radio — Хендоф (сессия 19.08.2026)

**Репозиторий:** github.com/novorossmebel-sys/city-radio (ветка `main`)
**Продолжение:** `docs/handoff_session_2026-08-17.md`. Там остановилась работа над источниками/фото/иллюстрациями. Сегодняшняя сессия — качественно другой уровень: владелец прислал полную редакционную политику проекта (23 раздела + системный промт) и попросил реализовать самую дорогую её часть — движок плановых дайджестов вместо потока карточек весь день.

**Важно:** как и в предыдущих сессиях, изменения пока не закоммичены. `git status` показывает 15 изменённых файлов и больше десятка новых (см. §6).

## 1. Задача и цель

Владелец прислал ~50 сообщений подряд с редакционной политикой канала, попросив дождаться команды «разбери» перед анализом. Ключевая мысль документа: **ПОСТ ≠ НОВОСТЬ ≠ СОБЫТИЕ** — у события должна быть память (что уже публиковали, что нового), а контент должен приходить не потоком карточек весь день, а тремя плановыми выпусками: **Morning Radar / Evening Digest / Weekly**.

Конкретный триггер: БПЛА-тревога у `@chpnvrsk_official` приходила в бот четырьмя отдельными постами («атака» → «отражение» → «отмена сигнала» → «угрозы нет»), потому что источник публикует так, а бот бездумно пересказывал каждый пост отдельно.

После разбора владелец сказал «давай с самого дорогого» — делать дайджест-движок сразу на все 19 рубрик / 35 каналов, одним заходом. Решено на этапе обсуждения:
- Критические алерты (БПЛА/вода/погода) остаются под ручным approve в боте — просто триггерятся автоматически, а не запуском скрипта вручную.
- Semantic-similarity дедуп (пороги 0.86/0.94 из документа) отложен — нет embeddings-инфраструктуры; вместо него сразу LLM-based дедуп по `event_key` (это и есть штатный fallback самого документа).
- `weather.py`/`currency.py`/`engine.py` не трогаются — не входят в дайджест, уже работают как решено раньше.

## 2. Что сделано — архитектура

Новый слой поверх существующего пайплайна, не замена. `verify_and_rewrite`, `build_structured_draft`, `_ensure_image`, вся фото-логика в [content/news.py](content/news.py) остались как есть и вызываются из нового кода.

```
sources.yaml (19 рубрик, 35 каналов)
        │
        ▼
[collect] периодический опрос каналов ── SQLite: channel_cursors
        │
        ▼
[pre-filter] keyword DROP (реклама/самопромо/engagement/пустой постер)
        │
        ▼
[classify+score] один вызов YandexGPT: рерайт + primary_type + entities/
   location/action (→ event_key) + под-рейтинги + флаги
        │
        ▼
[event dedup] сверка event_key с таблицей events (cooldown, novelty,
   статус-машина БПЛА THREAT→ALERT→ACTIVE→CANCELLED_BUT_THREAT→SAFE)
        │
        ├─ novelty==0 → DROP
        ├─ NOW (статус сменился / score≥90+актуально) → сразу в модерацию
        ├─ score≥70 → пул DIGEST (вечер)
        ├─ score≥60 → пул WEEKLY
        └─ иначе → ARCHIVE (не удаляется — для калибровки порогов позже)
        │
        ▼
[compose] по расписанию: Morning Radar 06:30 / юмор-подборка 18:00 /
   Evening Digest 19:00 / Weekly пятница 12:00 → карточки в тот же
   модерационный бот (approve/reject/edit без изменений)
```

### Новые файлы

| Файл | Назначение |
|---|---|
| [content/llm.py](content/llm.py) | Общий клиент YandexGPT (`call_yandexgpt`, `extract_json`), вынесен из news.py, чтобы не дублировать между news.py и digest_engine.py |
| [content/source_policy.py](content/source_policy.py) | Раздел 2 политики как код: `SOURCE_MAP` (роль/права каждого из ~21 явно расписанных каналов), списки ключевых слов для DROP-фильтров, `HUMOR_ONLY_CHANNELS`, `FACT_CINEMA_SOURCES`/`OPINION_CINEMA_SOURCES`, `HEALTH_CLAIM_TRIGGERS` |
| [content/digest_store.py](content/digest_store.py) | Первый в проекте слой на SQLite (`digest.db`) вместо JSON-файлов — нужны запросы вида «топ-N кандидатов рубрики X вне cooldown по score». Таблицы `candidates`, `events`, `channel_cursors`, `feedback` |
| [content/digest_engine.py](content/digest_engine.py) | Сбор кандидатов, pre-filter, классификация+скоринг, событийный дедуп, статус-машина БПЛА, маршрутизация NOW/DIGEST/WEEKLY/ARCHIVE |
| [content/digest_compose.py](content/digest_compose.py) | Сборка трёх плановых выпусков + юмористической подборки; группировка кинокандидатов по фильму с LLM-синтезом карточки «за/против/вердикт» вместо публикации каждого мнения отдельно |

### Изменения в существующих файлах

- **content/news.py** — рефакторинг без изменения логики: `_call_yandexgpt`/`_extract_json`/URL-константы вынесены в `content/llm.py`.
- **moderation.py** — добавлен публичный `send_text()` (для заголовков выпусков) + слой обратной связи (см. §3).

- **.gitignore** — добавлен `digest.db`.

## 3. Дополнительно: слой обратной связи (по ходу сессии)

Владелец, увидев опубликованные посты без реакций, спросил — нужно ли это настраивать. После уточнения, что кнопки реакций должны жить в приватном чате модерации (а не под постом в канале), реализовано:
- После approve пост публикуется как раньше, но статусное сообщение не самоудаляется — вместо него бот присылает карточку с кнопками 👍 полезно / 🔥 оч. интересно / 👎 не нужно / ♻️ уже знал.
- Реакция пишется в новую таблицу `feedback` (rubric, source_name, title, published_at, reaction), кнопки после нажатия убираются из сообщения.
- Осознанно **не делали** автоматическую перестройку весов рубрик/источников по этим данным — сначала 2–3 недели просто копим сырые реакции.

## 4. Баги — найдены на живых прогонах

1. **Несуществующий `_call_yandexgpt`/`json`** после рефакторинга в `content/llm.py` — `import json` в news.py потерялся при переносе (всё ещё нужен для `json.JSONDecodeError`), восстановлен.
2. **Необъявленная переменная `new_status`** в `digest_engine.py::_process_item` — при определённой комбинации (`event_key` пуст, но маршрут всё равно NOW через ветку score≥90) мог упасть `NameError`. Найдено вычиткой кода, не живым крашем. Исправлено инициализацией `new_status = None` до условного блока.
3. **`mark_event_published` нигде не вызывался** — cooldown по событиям не мог активироваться вообще (тихий логический пробел, не крэш). Добавлен вызов сразу после определения маршрута для NOW/DIGEST/WEEKLY.
4. **NOW-кандидаты не получали статус `sent_moderation`** после отправки в бот — при живом тесте кандидат id=2 навсегда оставался в статусе `scored`. Добавлен `update_candidate_status(..., "sent_moderation", digest_slot="now")` сразу после `bot.send_draft()`.
5. **Буферизованный stdout скрывал подтверждение запуска планировщика** — фоновый процесс с перенаправлением в файл по умолчанию блочно буферизуется. Перезапущен с флагом `-u` (небуферизованный).
6. **SQLite «database is locked» (3 раза подряд)** — параллельные задачи планировщика (быстрый/обычный опрос) одновременно бьют в `digest.db`, дефолтный busy-timeout SQLite (5 с) не хватало; вероятно усугублено тем, что проект лежит в папке OneDrive, которая может кратковременно держать файл во время синхронизации. Опасно тем, что молча роняло именно опрос алертных каналов (БПЛА/вода/погода). **Фикс:** `timeout=30` + `PRAGMA journal_mode=WAL` при подключении к БД (`content/digest_store.py::_connect`).
7. **Ошибочный диагноз «два дублирующих run.py moderate»** — попытка убить «дубликат» (`Stop-Process` по одному PID) на деле убила единственный логический процесс целиком, потому что на Windows фоновый процесс из git-bash всегда виден как пара parent+child PID с одинаковой командной строкой — это не два бота, а один. Замечено сразу (после kill список процессов был пуст), бот перезапущен без задержки, ошибка объяснена владельцу открыто.
8. **Устаревшие записи очереди модерации** — владелец вручную удалил старые сообщения через клиент Telegram (не через кнопки бота), из-за чего `moderation_state.json` продолжал считать их активными (несколько «зависших» draft_id, включая осиротевшую запись `awaiting_edit`). Исправлено остановкой бота (чтобы не сработало слияние состояния при следующем сохранении), прямой правкой `moderation_state.json` (`pending`/`awaiting_edit`/`photo_messages` → `{}`, `offset` сохранён) и перезапуском.

## 5. Что проверено живьём

- Сухой прогон `collect_candidates` на реальных каналах — маршрутизация выглядела разумно (реальный БПЛА-смежный пожароопасный алерт корректно ушёл в NOW; рутинный контент — в ARCHIVE/DIGEST/WEEKLY).
- NOW-путь: карточка приходит в бот сразу при обнаружении, не дожидаясь планового опроса.
- После фикса SQLite-блокировки — планировщик и бот модерации перезапущены и работают в фоне непрерывно (подтверждено на момент завершения сессии, см. §7).
- Слой реакций: карточка с кнопками появляется после approve, нажатие пишет `reaction` в БД и убирает кнопки.

## 7. Что не сделано / открытые задачи

1. **Ничего не закоммичено** (см. §6) — самый большой практический риск: вся эта работа существует только на локальной машине.
2. **Сутки живого прогона планировщика ещё не набраны.** Дайджест-движок проверен точечно (см. §5), но полный цикл — реальные 06:30/18:00/19:00 и пятничный Weekly — на момент завершения сессии ещё не отработал полностью без присмотра. Стоит понаблюдать за логами 5 новых задач планировщика перед тем, как полагаться на систему без присмотра.
3. **Semantic-similarity дедуп (embeddings, пороги 0.86/0.94)** — сознательно отложен, используется LLM event-key дедуп вместо него (см. §1).
4. **Отдельная таблица `movies`/`movie_id`** — группировка кинокандидатов в `digest_compose.py` сейчас упрощённая (сопоставление по названию текстом, не по ID), калибровка нужна после недели-двух реальных данных.
5. **Автоматическая перестройка весов по реакциям 👍🔥👎♻️** — намеренно отдельная будущая работа, сейчас только сбор сырых данных (см. §3).
6. **`digest.db-shm`/`digest.db-wal` не в `.gitignore`** — мелкая недоделка, см. §6.
7. Пункты, открытые ещё с сессии 17.08 и не тронутые сегодня: MAX-паблишер не проверен на живом токене, приватная группа вместо канала в Telegram, форма обратной связи от жителей, TMDB-ключ для постеров, «фотозаголовки» для ~16 рубрик без своей иллюстрации, перенос на VPS.

- **SQLite** (`digest.db`, WAL-режим) — новый персистентный слой, впервые в проекте помимо простых JSON-файлов.

- **Telegram Bot API** — карточки модерации и реакции, без изменений в протоколе, только новая логика вокруг существующих вызовов.
- **Windows PowerShell / git-bash** — управление фоновыми процессами (`run.py serve`, `run.py moderate`), диагностика через `Get-CimInstance Win32_Process`.
