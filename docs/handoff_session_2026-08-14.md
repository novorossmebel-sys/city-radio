# City Radio — Handoff (сессия 14.08.2026)

**Репозиторий:** github.com/novorossmebel-sys/city-radio (ветка `main`)
**Продолжение:** `docs/handoff_session_2026-08-13.md` (рубрики, инструменты чтения интернета) — тут только то, что нового за 14.08.

Сессия началась с вопроса «как вообще будет работать сбор контента и модерация» и закончилась рабочим end-to-end циклом: новость с сайта → рерайт через ИИ → модерация в Telegram с кнопками → публикация. По пути пришлось дважды менять план из-за внешних ограничений (не багов в коде) — обе истории ниже, это самое важное в этом файле.

---

## 1. Проблема №1: Anthropic API недоступен из России — решение: YandexGPT

**Что обнаружили:** при попытке оплатить Anthropic Console форма не даёт выбрать Россию/Гонконг/Китай страной биллинга. Проверили официальную страницу — это не баг формы, а сознательная политика:

> «Anthropic оставляет за собой право не предоставлять свои продукты и услуги организациям, чьё прямое или косвенное мажоритарное владение относится к странам, не входящим в список поддерживаемых регионов.» — [anthropic.com/supported-countries](https://anthropic.com/supported-countries)

Вторичные источники также утверждают, что IP проверяется на каждый запрос, не только при регистрации. Ключевой нюанс: ограничение привязано к **юрлицу** (владению), а не только к физическому местоположению человека — раз бизнес/ИП оформляется в России (как и планировалось по `docs/handoff.md`), обойти это переездом или VPN — не вариант, и мы сознательно не стали искать способ обойти.

**Решение:** переключили `content/news.py` на **YandexGPT** (Yandex Cloud AI Studio) — российский сервис, оплата рублями, без этой проблемы. Модель `yandexgpt/latest` (Pro), REST-эндпоинт `llm.api.cloud.yandex.net/foundationModels/v1/completion`, авторизация `Api-Key`. Цена ориентировочно 0.80 ₽/1000 токенов — при наших объёмах (15-20 коротких вызовов/день) это копейки.

**Особенность:** в отличие от Claude, YandexGPT не даёт гарантированный structured output (JSON-схему) — модель иногда возвращает обычный текст-отказ вместо JSON (сработали фильтры безопасности, даже на нейтральные на вид новости). `verify_and_rewrite()` в `content/news.py` это обрабатывает: при неудачном парсинге JSON черновик всё равно создаётся, помечается `needs_manual_review=True` с текстом отказа в `concerns`, и уходит на ручную проверку — а не роняет весь процесс.

## 2. Проблема №2: `api.telegram.org` заблокирован на сети — решение: VPN на время тестов

**Что обнаружили:** прямой `curl`/`requests` до `api.telegram.org` обрывается на TLS-хендшейке (`SSLEOFError`) — блокировка на уровне провайдера, не сбой кода. Это уже второй раз всплывает такая находка (то же самое зафиксировано в handoff другого проекта пользователя от 08.08.2026 — «Telegram API заблокирован без VPN»).

**Что пробовали:** VPN-приложение Browsec (десктопное, не браузерное расширение). Пытались настроить точечную маршрутизацию только процесса `.venv\Scripts\python.exe` (split tunneling) — не сработало: IP не менялся, сколько ни настраивали список приложений. Вероятно, у десктопной версии Browsec такой функции по факту нет (или не работает), несмотря на ожидания.

**Решение (рабочее, но временное):** включать Browsec **полностью** (весь трафик компьютера) на время локальных тестов Telegram — после включения `api.telegram.org` сразу заработал (проверено сравнением публичного IP до/после и живым запросом `getMe`). Для продакшена это не потребуется вообще — сервис будет на VPS с незаблокированной сетью (см. цели ниже).

## 3. Что собрано и проверено живым тестом

| Файл | Что делает |
|---|---|
| `content/base.py` | + `Draft` — черновик с метаданными для модерации (источник, оригинал, замечания), отдельно от готового `Post` |
| `content/news.py` | `RssSource` (рабочий адаптер, проверено на `novorab.ru`) + `verify_and_rewrite()` через YandexGPT + обработка отказов модели |
| `moderation.py` | Бот-модератор: черновик с кнопками ✅Опубликовать/✏️Править/❌Отклонить в личку владельцу; правка — ответом в чат; публикация по одобрению: MAX → пауза 30-40 сек → Telegram |
| `run.py` | + команды `test-news`, `test-news-moderate`, `moderate` |
| `config.py` / `.env` | + `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `TELEGRAM_BOT_TOKEN` (новый бот `Radio_max_bot_bot`, создан отдельно от двух уже существующих ботов пользователя — переиспользование чужого токена сломало бы long polling обоих сразу), `OWNER_TELEGRAM_CHAT_ID` |

**Живой тест (успешно, целиком):** реальная новость с `novorab.ru` → YandexGPT переписал → пришло в Telegram-личку с кнопками → нажали «Править» → ответили текстом → бот пересобрал черновик → нажали «Опубликовать» → пауза → «Опубликовано ✅» (публикация в MAX/Telegram тихо пропущена — каналы в `cities.yaml` пока не заполнены, это ожидаемо).

**Найденный по ходу архитектурный баг:** очередь черновиков (`pending`) в `moderation.py` хранится в памяти конкретного процесса. Если отправка черновика и приём кнопок происходят в **разных** процессах (так и тестировали сначала — фоновый `moderate` + разовый `test-news-moderate`) — второй процесс не видит черновики первого, кнопки отвечают «черновик устарел». Починили для теста (свели в один процесс), но для продакшена стоит иметь в виду: пока это не проблема (будет один непрерывный процесс), но при росте/масштабировании `pending` нужно вынести в файл/БД, чтобы переживало перезапуск.

## 4. Следующий шаг начат, не закончен: подключение Telegram-источников (novosti_efir, chpnvrsk_official)

**Важное открытие:** «через Bot API», как изначально планировали — не сработает. Bot API отдаёт боту новые посты канала (`channel_post`) только если бот **сам администратор** этого канала. `novosti_efir` и `chpnvrsk_official` — чужие независимые каналы, добавить туда своего бота админом нельзя.

**Реальный путь:** MTProto через библиотеку **Telethon** — логин обычным Telegram-аккаунтом-пользователем (не ботом), как если бы зашли с телефона. Такой аккаунт может читать историю любого публичного канала без каких-либо прав администратора.

**Что для этого нужно (не сделано):**
1. `api_id` + `api_hash` с https://my.telegram.org (вход по номеру телефона → API development tools).
2. Номер телефона для входа — решение не принято: основной аккаунт пользователя (проще) или отдельный «аккаунт-наблюдатель» (безопаснее для основного аккаунта, но нужна ещё одна симка/номер).
3. Один интерактивный вход с кодом подтверждения из Telegram (по аналогии с тем, как передавали токены — код скажет пользователь, авторизация завершится один раз, дальше сессия сохраняется).

Код `TelegramChannelSource` под Telethon ещё не написан — остановились на решении по пункту 2.

## 6. Известные ограничения/риски на заметку

- `moderation.py`: состояние только в памяти процесса — теряется при перезапуске (см. §3).
- `api.telegram.org` заблокирован локально без VPN — на время любых локальных тестов Telegram нужен включённый Browsec (полный режим, не выборочный).
- MAX-паблишер по-прежнему не проверен на живом токене (см. предыдущий handoff — неопределённость с базовым URL и форматом заголовка авторизации).
- YandexGPT иногда отказывается отвечать по фильтрам безопасности даже на нейтральные новости — учитывать при выборе источников/рубрик, не только при происшествиях.
- Токен нового Telegram-бота (`Radio_max_bot_bot`) в какой-то момент был вставлен прямо в чат пользователем — сохранён в `.env`, в открытом виде больше не выводился; при желании можно перевыпустить через `/revoke` у @BotFather для подстраховки.
